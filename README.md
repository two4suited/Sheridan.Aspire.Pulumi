# aspire.pulumi.packages

## Pulumi integration

`AppHost.cs` declares a Pulumi stack with `builder.AddPulumiStack("aspire-pulumi-packages", "dev").WithOrganization("two4suited")`. There is no separate Pulumi project; it is generated by the Aspire pipeline:

- `aspire publish` writes `Pulumi.yaml` and `Pulumi.<stack>.yaml` (which imports the ESC environment) to `<output>/<name>/pulumi/`.
- `aspire deploy` then checks `pulumi whoami` (run `pulumi login` first), creates the ESC environment and stack if missing, and runs `pulumi up`. State lives in Pulumi Cloud.
- `aspire do pulumi-destroy-<name>` / `aspire destroy` runs `pulumi destroy`.

The stack name defaults to the lower-cased Aspire environment, so `aspire deploy -e test` targets stack `test` and `aspire deploy -e prod` targets `prod` (pass a second argument to `AddPulumiStack` to pin it).

Both can also be passed at the command line, overriding the code: `aspire deploy -- --Pulumi:Stack=qa --Pulumi:Esc=shared/qa,myproj/qa` (comma-separated list; also settable via config or the `Pulumi__Stack` / `Pulumi__Esc` environment variables).

Use `.WithEscEnvironment("project/env1", "project/env2")` to import one or more existing ESC environments (later ones override earlier ones); with none specified, `<name>/<stack>` is used and created on deploy if missing.

The code is split across three class libraries under `src/`: `AspirePulumiPackages.Pulumi` (the stack/pipeline/YAML-generation core — `PulumiStackResource`, `PulumiProgram`, `PulumiCli`, `PulumiOutputReference`, `AddPulumiStack`/`DependsOnStack`/etc.), `AspirePulumiPackages.Pulumi.Azure` (the shared managed-identity interface); Cosmos DB lives in `AspirePulumiPackages.Pulumi.Azure.CosmosDB`; the Container Apps environment lives in `AspirePulumiPackages.Pulumi.Azure.AppContainers` (port of `Aspire.Hosting.Azure.AppContainers`: `WithAzureContainerRegistry`, `WithAzureLogAnalyticsWorkspace`, `WithAcrPullIdentity`, `WithDashboard`, VNet via `WithDelegatedSubnet`, and `PublishAsPulumiContainerAppJob`/`PublishAsScheduledPulumiContainerAppJob`), and `AspirePulumiPackages.Pulumi.Entra` (the Azure AD app registration). Azure and Entra both depend on the core project; `AspirePulumiPackages.AppHost` references all three.

## Resource naming

Azure names are built from the app (Pulumi project) name, the Aspire resource name and the stack name, shortened deterministically (with a hash only when lossy) to fit each resource type's limits, and can be pinned with `WithAzureName(AzureNameKind.X, "name")`. See [docs/naming.md](docs/naming.md) for the scheme and the per-resource rule table.

## Container Apps environment

`builder.AddPulumiAzureContainerAppEnvironment("aca-env")` is the Pulumi equivalent of Aspire's `AddAzureContainerAppEnvironment`. It is a compute environment, so resources opt in the usual way:

```csharp
var acaEnv = builder.AddPulumiAzureContainerAppEnvironment("aca-env");
builder.AddProject<Projects.AspirePulumiPackages_Api>("api")
    .WithExternalHttpEndpoints()
    .WithComputeEnvironment(acaEnv);
```

`aspire publish` writes the resource group, Log Analytics workspace, container registry, pull identity (AcrPull) and managed environment, plus a `ContainerApp` per targeted resource. `aspire deploy` runs: `pulumi-provision` (login, ESC, `pulumi up --target` for all the stack's non-app infrastructure incl. the registry) → `build-<resource>` → `push-<resource>` → `pulumi-deploy` (full `pulumi up`). Images are tagged with a per-deploy timestamp so each deploy creates a new revision.

#### How `aspire deploy` orders things (one deploy is enough)

Each `PulumiStackResource` contributes `pulumi-publish` → `pulumi-provision` → `pulumi-deploy` steps. The generated `PulumiProgram` is split in two halves: **app resources** (container apps, web apps, Kubernetes workloads and in-cluster objects, registered with `program.AddAppResource(...)` or inside `program.BeginAppScope()` by the compute environments) and **infrastructure**, which is the default for everything else, so integrations (Cosmos, Storage, Service Bus, Key Vault, SQL, ...) need no changes. Infrastructure that references an app is treated as part of the app half.

1. `pulumi-provision` runs `pulumi up --target` for *every* infrastructure resource (not only the registry), so all stack outputs that apps consume (Cosmos endpoints, storage endpoints, Service Bus hosts, ...) exist.
2. Images are built and pushed (they need the registry from step 1).
3. `pulumi-deploy` regenerates the program — the environment variables that read stack outputs now resolve — and runs the full `pulumi up`, creating the apps.

Aspire relationships drive the ordering between stacks: when a resource hosted in stack *S* references (`WithReference`, an endpoint/connection string/`PulumiOutputReference` in its environment) or `WaitFor`s a resource in stack *T*, *S*'s provision step automatically depends on *T*'s deploy step. `DependsOnStack` is only needed for dependencies Aspire can't see. A deferral (`Deferring environment variable ...`) is logged at debug level while the first generation runs (and in `aspire publish`, which has no real stack) and as a warning only if an output is still missing after the provision pass.

## Cosmos DB

`builder.AddPulumiCosmosDB("cosmos")` is the Pulumi equivalent of Aspire's `AddAzureCosmosDB`: a serverless NoSQL API account with Entra-only auth (`disableLocalAuth: true` — no connection-string keys in the cloud). Databases and containers are added the same way as the official integration:

```csharp
var cosmos = builder.AddPulumiCosmosDB("cosmos")
    .WithPulumiStack(azureStack)
    .RunAsEmulator();
cosmos.AddCosmosDatabase("appdb").AddContainer("items", "/id");

builder.AddProject<Projects.AspirePulumiPackages_Api>("api")
    .WithComputeEnvironment(acaEnv)
    .WithReference(cosmos);
```

Package: `AspirePulumiPackages.Pulumi.Azure.CosmosDB` (port of `Aspire.Hosting.Azure.CosmosDB`; `AddPulumiAzureCosmosDB` remains as an alias). Also supported: `AddCosmosDatabase(name, databaseName?)`/`AddContainer(name, partitionKeyPath(s), containerName?)` with per-database/container connection strings, `WithDefaultAzureSku()` (non-serverless), `RunAsEmulator`/`RunAsPreviewEmulator`/`RunAsClassicEmulator` (+ `WithDataVolume`, `WithGatewayPort`, `WithPartitionCount`, `WithDataExplorer`), `ConfigureInfrastructure(i => i.CosmosDBAccount.Set(...))`, and `WithAccessKeyAuthentication()`, which keeps local auth on and stores the account/database/container connection strings and primary key as secrets in a Key Vault created for the account (consumers get Key Vault Secrets User; the connection string expression resolves to the secret URI, as with `AddPulumiAzureKeyVault(...).GetSecret`).

`.RunAsEmulator()` runs the Cosmos DB NoSQL API emulator container locally (no effect in publish mode) so `aspire run` works without any Azure resources. `aspire publish`/`aspire deploy` provision the real account, database(s) and container(s) instead.

`.WithReference(cosmos)` on a project is enough to get data access — no separate role-assignment call is needed. Any compute environment (e.g. `AddPulumiAzureContainerAppEnvironment`) hosting a resource that references the Cosmos DB account automatically gets a Pulumi `SqlResourceSqlRoleAssignment` granting its shared managed identity the built-in **Cosmos DB Built-in Data Contributor** role, scoped to the account — the data-plane equivalent of the ACR pull role assignment described above. `ConnectionStrings__cosmos` (the account's document endpoint, consumed by `Microsoft.Azure.Cosmos`/`Aspire.Microsoft.Azure.Cosmos` with `DefaultAzureCredential`) is read from the stack's outputs the same way `AzureAd__ClientId` is above, and resolves on the first deploy because the provision pass creates the account before the program is regenerated for the deploy pass (see "How `aspire deploy` orders things" below).

## Storage

`AspirePulumiPackages.Pulumi.Azure.Storage` ports `Aspire.Hosting.Azure.Storage`. `builder.AddPulumiStorage("storage")` (alias `AddPulumiAzureStorage`) provisions a StorageV2 / Standard_GRS / TLS1_2 account with shared-key access disabled, matching the Bicep the official integration generates. `AddBlobs`/`AddQueues`/`AddTables`, `AddBlobContainer` and `AddQueue` mirror the official API, and `.RunAsEmulator()` runs Azurite locally. `WithReference(blobs)` (or the queue/table/container/queue resources) grants the hosting compute environment's identity the matching *Storage Blob/Queue/Table Data Contributor* role. The storage account name is auto-generated by the azure-native provider.

## Azure Functions

`AspirePulumiPackages.Pulumi.Azure.Functions` ports `Aspire.Hosting.Azure.Functions`. `builder.AddPulumiAzureFunctionsProject("func", "../MyFunctions/MyFunctions.csproj")` (or `<TProject>`; alias `AddPulumiFunctionsProject`) mirrors `AddAzureFunctionsProject`: a `ProjectResource` that sets the Functions environment variables (`FUNCTIONS_WORKER_RUNTIME`, OpenTelemetry mode, `ASPNETCORE_URLS`) and wires host storage as `AzureWebJobsStorage__{blob,queue,table,dataLake}ServiceUri` (identity-based).

```csharp
var storage = builder.AddPulumiStorage("storage").WithPulumiStack(azureStack).RunAsEmulator();
var blobs = storage.AddBlobs("blobs");

builder.AddPulumiAzureFunctionsProject("func", "../MyFunctions/MyFunctions.csproj")
    .WithPulumiStack(azureStack)      // binds the implicit host storage account
    // .WithHostStorage(storage)      // or use your own Pulumi storage account instead of the implicit one
    .WithReference(blobs)             // injects blobs__blobServiceUri etc. (not ConnectionStrings__blobs), as upstream
    .WithComputeEnvironment(acaEnv);
```

By default an implicit `funcstorage<hash>` storage account is created (Azurite in run mode; dropped from the model if every project uses `WithHostStorage`). Deployed through `AddPulumiAzureContainerAppEnvironment`, the container app gets `kind: functionapp` (KEDA scale rules follow the triggers), `http` ingress and no 1-replica cap; the environment identity is granted Storage Blob/Queue/Table Data Contributor (via the Storage integration) plus Storage Account Contributor on the host storage, matching the official Bicep. The compute environment hook is `PulumiContainerAppCustomizationAnnotation` in `AspirePulumiPackages.Pulumi.Azure`. Not ported: launch-profile port discovery in run mode, `AZURE_CLIENT_ID` injection (the shared environment identity is not exposed with a client id yet), the Durable Task scheduler APIs. Like the other integrations, storage endpoints are read from stack outputs, which the first `aspire deploy` creates in its provision pass.

## Search

`AspirePulumiPackages.Pulumi.Azure.Search` ports `Aspire.Hosting.Azure.Search`. `builder.AddPulumiSearch("search")` (alias `AddPulumiAzureSearch`) provisions an `azure-native:search:Service` matching the Bicep the official integration generates: `basic` SKU, 1 partition, 1 replica, `hostingMode: default` and local (key) auth disabled, with outputs `Endpoint` (`https://<name>.search.windows.net`), `Name` and `Id`. The connection string is `Endpoint=<endpoint>`. `WithReference(search)` grants the hosting compute environment's identity *Search Index Data Contributor* and *Search Service Contributor* (the official defaults); `WithRoleAssignments(search, AzureSearchRole.SearchIndexDataReader, ...)` replaces them. `WithSku("standard")` is an addition for choosing another tier, and `ConfigureInfrastructure(infra => infra.SearchService.Set("replicaCount", 3))` edits the generated resource (see `docs/provisioning.md`). The service name is auto-generated by the azure-native provider. Not ported: `PublishAsExisting`/`AsExisting`, and a local emulator (the official integration has none).

## Service Bus

`AspirePulumiPackages.Pulumi.Azure.ServiceBus` ports `Aspire.Hosting.Azure.ServiceBus`. `builder.AddPulumiServiceBus("messaging")` (alias `AddPulumiAzureServiceBus`) provisions a Standard-SKU namespace with local auth disabled, matching the official Bicep (outputs `serviceBusEndpoint`, `serviceBusHostName`, `name`, `id`). `AddServiceBusQueue`/`AddServiceBusTopic`/`AddServiceBusSubscription` (plus the `AddQueue`/`AddTopic`/`AddSubscription` forms) and `WithProperties(...)` on queues, topics and subscriptions mirror the official API, including `Rules` (correlation filters) on subscriptions.

```csharp
var sb = builder.AddPulumiServiceBus("messaging").WithPulumiStack(azureStack);
sb.AddServiceBusQueue("orders").WithProperties(q => q.MaxDeliveryCount = 5);
sb.AddServiceBusTopic("events").AddServiceBusSubscription("audit");

builder.AddProject<Projects.AspirePulumiPackages_Api>("api").WithReference(sb).WithComputeEnvironment(acaEnv);
```

`WithReference` of the namespace, a queue, a topic or a subscription grants the hosting compute environment's identity *Azure Service Bus Data Owner* on the namespace (the official default); `WithRoleAssignments(sb, AzureServiceBusRole.AzureServiceBusDataSender, ...)` replaces it. The namespace name is auto-generated by the azure-native provider. Not ported: `RunAsEmulator` (the Service Bus emulator) and its configuration APIs.

## Azure OpenAI (Cognitive Services)

`AspirePulumiPackages.Pulumi.Azure.CognitiveServices` ports `Aspire.Hosting.Azure.CognitiveServices` (the official package only ships `AddAzureOpenAI`). `builder.AddPulumiOpenAI("openai")` (aliases `AddPulumiAzureOpenAI`, `AddPulumiCognitiveServices`) provisions an `azure-native:cognitiveservices:Account` of kind `OpenAI` (S0, local auth disabled, public access enabled), matching the generated Bicep. `AddDeployment("chat", "gpt-4o", "2024-08-06")` adds a model deployment (`WithProperties` sets `DeploymentName`, `SkuName`, `SkuCapacity`; defaults Standard / 8, deployments are chained with `dependsOn` as in the official Bicep). `WithReference(openai)` or `WithReference(deployment)` grants the hosting compute environment's identity *Cognitive Services OpenAI User*; `WithRoleAssignments(openai, AzureOpenAIRole.…)` replaces that. Connection strings are `Endpoint=<endpoint>` / `Endpoint=<endpoint>;Deployment=<name>`. `ConfigureInfrastructure(infra => infra.CognitiveServicesAccount.Set("properties.publicNetworkAccess", "Disabled"))` edits the Pulumi resources (see `docs/provisioning.md`). The account name is auto-generated by the provider; the custom sub-domain is `<name><first segment of the subscription id>` (override with `CustomSubDomainName`) instead of Bicep's `uniqueString(resourceGroup().id)`. Not ported: private endpoint / network security perimeter association, `PublishAsExisting`.

## Microsoft Foundry

`AspirePulumiPackages.Pulumi.Azure.Foundry` ports `Aspire.Hosting.Foundry` (`AddFoundry`). `builder.AddPulumiFoundry("foundry")` (alias `AddPulumiAzureAIFoundry`) provisions an `azure-native:cognitiveservices:Account` of kind `AIServices` (S0, system-assigned identity, local auth disabled, `allowProjectManagement`) plus an account capability host (`foundry-caphost`, kind `Agents`, `enablePublicHostingEnvironment: true`), matching the generated Bicep. The capability host uses the GA `azure-native:cognitiveservices/v20251201:AccountCapabilityHost` type because azure-native's default `CapabilityHost` type does not expose `enablePublicHostingEnvironment` (its settings live under `properties.` for `ConfigureInfrastructure`). `AddDeployment("chat", FoundryModel.OpenAI.Gpt4o)` adds a deployment from the model catalog (`FoundryModel`, generated from the official package without the Foundry Local-only models; `project.AddModelDeployment(...)` is the same on a project), or `AddDeployment("chat", "gpt-4o", "2024-08-06", "OpenAI")` by name (`WithProperties` sets `DeploymentName`, `ModelName`, `ModelVersion`, `Format`, `SkuName`, `SkuCapacity`; defaults GlobalStandard / 1; deployments are chained with `dependsOn`). `AddProject("agents")` adds an `accounts/projects` project (system-assigned identity) with an Application Insights component, a *Monitoring Metrics Publisher* grant for the project identity and the `AppInsights` project connection, as the Bicep does.

Project options mirror the official ones. `WithAppInsights(appInsights)` uses a `AddPulumiApplicationInsights` resource instead of creating a component; `WithKeyVault(keyVault)` adds the Key Vault connection (project identity gets *Key Vault Secrets Officer*; every other connection depends on it); `AddConnection(storage | cosmos | search | containerRegistry)` adds the project connection plus the project-identity role assignments the official integration creates (Storage Blob Data Contributor; Search Index Data Contributor and Search Service Contributor); `AddConnection(name, ctx => properties)` adds a raw `ProjectConnection`; `AddBingGroundingConnection(name, bingResourceId, apiKeyParameter)` adds the account-level `GroundingWithBingSearch` connection. `AddCapabilityHost("ch").WithCosmosDB(cosmos).WithStorage(storage).WithSearch(search)` (optionally `.WithAzureOpenAI(foundry)`) adds the project capability host with its Storage / Cosmos DB / Search / Azure OpenAI connections and role assignments (Cosmos: the built-in *Data Contributor* SQL role). The connected resources must be provisioned in the same Pulumi stack as the Foundry account, because the program references them directly. Connection names are deterministic (a hash of project and target) instead of the official random guid, so they do not churn the Pulumi state.

`PublishAsExisting("name", "resource-group")` (alias `AsExisting`) looks the account up with `getAccount` instead of creating it; deployments, projects, the capability host and role assignments are still applied to it. Adding a private endpoint (`subnet.AddPrivateEndpoint(foundry)` from the Network project) sets `publicNetworkAccess: Disabled`, uses private link group `account` and registers the endpoint in `privatelink.cognitiveservices.azure.com`, `privatelink.services.ai.azure.com` and `privatelink.openai.azure.com`, as the official integration does (the Network project's `IPulumiPrivateEndpointTarget` gained an optional `AdditionalPrivateDnsZoneNames` for this); the account also works with `WithNetworkSecurityPerimeter`. `RunAsFoundryLocal("http://localhost:5272/v1/")` is a no-op in publish mode like the official method, and in run mode points the connection string at an already running Foundry Local service (`Endpoint=<endpoint>;Key=unused`, deployments `…;Model=<model>`).

`WithReference(foundry)`, `WithReference(deployment)` or `WithReference(project)` grants the hosting compute environment's identity *Cognitive Services User* and *Cognitive Services OpenAI User* on the account; `WithRoleAssignments(foundry, FoundryRole.…)` replaces that. Connection strings: account `Endpoint=<endpoint>;EndpointAIInference=<AI Foundry API endpoint>models`, deployment `…;Deployment=<name>`, project `Endpoint=<project endpoint>`. `ConfigureInfrastructure(infra => infra.CognitiveServicesAccount.Set(...))` edits the Pulumi resources (`CognitiveServicesAccount`, `CapabilityHost`, `Deployments`, `Projects`, `ProjectCapabilityHosts`, `Connections`; see `docs/provisioning.md`). The account name is auto-generated by the provider; the custom sub-domain is `<name><first segment of the subscription id>` (override with `CustomSubDomainName`). The demo AppHost provisions an account and a project (connected to the demo storage and search) but no model deployment.

Prompt agents are Foundry data-plane objects, so Pulumi cannot manage them: `project.AddPromptAgent("helper", deployment, "instructions")` creates a pipeline step (`deploy-helper`, tagged `deploy-compute`) that runs after the stack has deployed and creates an agent version through `AIProjectClient` with `DefaultAzureCredential` (the deploying principal needs *Azure AI User* on the project; the step retries while the project endpoint is not ready yet). The agent's connection string is `<project endpoint>/agents/<name>` (also `AgentName`, `ProjectEndpoint`) and `agent.Resource.Version` holds the deployed version. Tools mirror the official ones and are attached with `WithTool(...)`: `AddCodeInterpreterTool`, `AddFileSearchTool(name, vectorStoreIds)`, `AddWebSearchTool`, `AddImageGenerationTool`, `AddComputerUseTool`, `AddAISearchTool(name, index).WithReference(search)` (adds the project connection), `AddBingGroundingTool(name).WithReference(connection)` or `.WithReference(bingResourceId, apiKeyParameter)`, `AddSharePointTool`, `AddFabricTool`, `AddFunctionTool`, `AddAzureFunctionTool` and `WithCustomTool(IFoundryTool)`. Differences: no run-mode deployment before start and no *Send Message* dashboard command (the project only exists after a deploy), and prompt agents are deleted with the project rather than by a destroy step. Verified with unit tests of the agent definitions only, not against a deployed Foundry project.

Toolboxes: `project.AddToolbox("tools").WithWebSearchTool().WithMcpTool("docs", "https://…/mcp")` (string, `EndpointReference` or `ReferenceExpression`; the endpoint must be Foundry-reachable HTTPS) `.WithAISearchTool("search", search, "index")` (adds the project connection) `.WithDescription(...)`. A `deploy-<name>` step reconciles the toolbox through the Agents data plane after the stack deploys, like the official one: it creates a version only when the configuration hash differs from the current default, promotes it, and refuses to touch a toolbox Aspire does not manage (`aspire-managed-by` metadata). `toolbox.Resource.DeployedVersion` holds the version; the connection string is the toolbox MCP endpoint. Unit tested only, not against a deployed project.

Not ported, and why:

- **Provider gaps (azure-native)**: the *project* capability host cannot set `capabilityHostKind` / `enablePublicHostingEnvironment` (every azure-native API version of `ProjectCapabilityHostProperties` only has the four connection lists; the account capability host does expose them); the Bing grounding key cannot be read with `listKeys()` (azure-native has no `Microsoft.Bing` provider), so `AddBingGroundingConnection` takes the key as a secret parameter instead of the official overload that only needs the resource id.
- **Foundry hosted agents — still to port**: `AsHostedAgent` / `PublishAsHostedAgent`, the project as an Aspire compute environment with its container registry, agent versions and image push need a Sandboxes-style pipeline port (image build/push, reconciliation, destroy) that cannot be verified without a deployed project. Toolbox gaps: run-mode deployment, the tool-discovery readiness probe, `AsExisting` / `RunAsExisting` / `PublishAsExisting`, MCP approval policies and the `Version` pin.
- **Foundry Local lifecycle**: the official `RunAsFoundryLocal()` also starts the local service and downloads / loads models (`Microsoft.AI.Foundry.Local`), and `FoundryModel.Local` lists the local-only models. That is a run-mode feature with nothing to do with Pulumi; here you pass the endpoint of a service you started yourself.
- The `endpoints["AI Foundry API"]` output expressions and the new connections were verified with `aspire publish` only, not deployed against Azure.

## SignalR

`AspirePulumiPackages.Pulumi.Azure.SignalR` ports `Aspire.Hosting.Azure.SignalR`. `builder.AddPulumiSignalR("signalr")` (alias `AddPulumiAzureSignalR`, optional `AzureSignalRServiceMode.Serverless`) provisions an `azure-native:signalrservice:SignalR` matching the official Bicep: kind `SignalR`, SKU `Free_F1` (capacity 1), local auth disabled, CORS `*`, and the `ServiceMode` feature (outputs `hostName`, `name`, `id`). The connection string is `Endpoint=https://{hostName};AuthType=azure`.

```csharp
var signalr = builder.AddPulumiSignalR("signalr")
    .WithPulumiStack(azureStack)
    .WithSku("Standard_S1")   // Pulumi addition; the official default Free_F1 is kept otherwise
    .ConfigureInfrastructure(infra => infra.SignalRService.Set("cors.allowedOrigins", new[] { "https://example.com" }));

builder.AddProject<Projects.AspirePulumiPackages_Api>("api").WithReference(signalr).WithComputeEnvironment(acaEnv);
```

`WithReference` grants the hosting compute environment's identity *SignalR App Server* on the service (the official default); `WithRoleAssignments(signalr, AzureSignalRRole.SignalRRestApiOwner, ...)` replaces it. `ConfigureInfrastructure` exposes the `SignalRService` root (see `docs/provisioning.md`). The service name is auto-generated by the azure-native provider. Not ported: `RunAsEmulator` and the `SignalRBuiltInRole` (Azure.Provisioning) overload of `WithRoleAssignments`.

## Connector Namespace

`AspirePulumiPackages.Pulumi.Azure.ConnectorNamespace` ports `Aspire.Hosting.Azure.ConnectorNamespace` (preview). **azure-native has no `Microsoft.Web/connectorGateways` resource** (confirmed with `pulumi package get-schema azure-native`), so the namespace is provisioned as a single `azure-native:resources:Deployment` (an ARM template deployment) containing exactly the resource types, `2026-05-01-preview` API version and properties of the official generated Bicep: the gateway (`conns<uniqueString>`, system-assigned identity), connections, connection access policies, `mcpserverConfigs` (`ManagedMcpServer`, state `Enabled`) and MCP access policies. Outputs: `Id`, `Name`, `PrincipalId`, `TenantId`.

```csharp
var connectors = builder.AddPulumiConnectorNamespace("connectors").WithPulumiStack(azureStack).WithResourceGroup(rg);
var office = connectors.AddConnection("office", "office365")
    .WithAccessPolicy("owner", new() { ObjectId = "<guid>", TenantId = "<guid>" })
    .WithIdentityAccessPolicy("app", appIdentity);   // a PulumiAzureUserAssignedIdentityResource in the same stack
connectors.AddMcpServerConfig("mcp", new() { Description = "Mail tools" })
    .WithConnector("office-tools", office, new() { Operations = [new() { Name = "SendEmail" }] })
    .WithAccessPolicy("user", new() { ObjectId = "<guid>", TenantId = "<guid>", PrincipalType = AzureConnectorNamespaceMcpAccessPolicyPrincipalType.User });

builder.AddProject<Projects.AspirePulumiPackages_Api>("api").WithReference(office);   // {name}__connectorGatewayName / {name}__connectionName
```

`ConfigureInfrastructure(infra => ...)` exposes the `Deployment` root plus the ARM template's `TemplateResources`/`Gateway` maps (ARM property names, not azure-native names). `PublishAsExisting(name, resourceGroup)` / `AsExisting(name, resourceGroup)` on the namespace uses an existing gateway: the template drops the gateway resource (children are deployed under the existing gateway name, in that resource group, without `dependsOn` on it) and the outputs read the existing gateway; connection- and MCP-config-level `AsExisting` work as before. Not ported: the Aspire polyglot (ATS) exports. **Provider gap (checked against the current azure-native schema; azapi is not available as a Pulumi package):** azure-native has no `connectorGateways` resource family (the only similar `azure-native:web:ConnectionGateway` is the unrelated Logic Apps `Microsoft.Web/connectionGateways`), so no typed resource can replace the ARM-template Deployment; per-resource diffs are therefore not available, only a diff of the template. Revisit when azure-native publishes the `2026-05-01-preview` Microsoft.Web specs. Not demonstrated in `AppHost.cs` because connections need real Entra object ids and interactive OAuth consent. Note that connections using OAuth must still be consented in the portal after deployment, as with the Bicep version. The ARM template route was verified by comparing `aspire publish` output against the official Bicep, not by a real deployment.

## Front Door

`AspirePulumiPackages.Pulumi.Azure.FrontDoor` ports `Aspire.Hosting.Azure.FrontDoor`. `builder.AddPulumiFrontDoor("frontdoor")` (alias `AddPulumiAzureFrontDoor`) provisions a global `azure-native:cdn:Profile` (`Standard_AzureFrontDoor`) and, for each `WithOrigin(resource)`, an `AFDEndpoint`, an `AFDOriginGroup` (health probe from the origin's `EndpointProbeAnnotation`, default `/` over HTTPS; load balancing 4/3/50), an `AFDOrigin` (host and host header = the app's FQDN) and a `/*` `Route` (HttpsOnly forwarding, HTTPS redirect, linked to the default domain), matching the generated Bicep. Each origin gets its own `*.azurefd.net` URL, output as `{frontdoor}{origin}EndpointUrl` and exposed as `GetEndpointUrl("api")`.

```csharp
var api = builder.AddProject<Projects.Api>("api").WithExternalHttpEndpoints().WithComputeEnvironment(acaEnv);
builder.AddPulumiFrontDoor("frontdoor")
    .WithPulumiStack(azureStack).WithResourceGroup(sharedRg)
    .WithOrigin(api)
    .ConfigureInfrastructure(infra => infra.GetRoute("api").Set("patternsToMatch", new[] { "/api/*" }));
```

`ConfigureInfrastructure` exposes `Profile`, `GetEndpoint/GetOriginGroup/GetOrigin/GetRoute(originName)` (see `docs/provisioning.md`). Origins must be hosted by an Azure Container Apps or App Service environment (the origin host is read from the emitted container app / web app) in the **same Pulumi stack**, and need an external HTTP(S) endpoint. Not demoed in `AppHost.cs` (a Standard profile has a fixed monthly base fee); verified with a temporary AppHost publish. Not ported: custom domains, WAF/security policies, rule sets, Premium SKU or other origin types (e.g. non-Aspire hosts), and Bicep's deterministic `uniqueString` names (the provider auto-names the sub-resources; azure-native endpoint names are limited to 46 characters).

## Container Apps Sandboxes

`AspirePulumiPackages.Pulumi.Azure.Sandboxes` ports `Aspire.Hosting.Azure.Sandboxes` (preview upstream). `builder.AddPulumiSandboxGroup("sandboxes")` (aliases `AddPulumiAzureSandboxGroup`, `AddPulumiSandboxes`) is a compute environment, like `AddAzureSandboxGroup`. Compute resources that target it are built (linux/amd64), pushed to the group's registry and deployed as sandboxes.

It is split along the line where Pulumi stops being able to manage things:

- **Pulumi (ARM) half**: the sandbox group, a Basic container registry (`sandboxes-acr`), a dedicated image-pull identity (`sandboxes-mi`) with *AcrPull* on it, and *Container Apps SandboxGroup Data Owner* for the deploying principal (outputs `id`, `name`, `location`, `resourceGroup`, `subscriptionId`, `imagePullIdentityClientId`, registry name and login server).
- **Pipeline (data plane) half**: the disk images, sandboxes, lifecycle policies and ports are not ARM resources. They live on the Azure Dev Compute data plane (`https://management.{region}.azuredevcompute.io`), which neither azure-native nor azapi models (azapi's data-plane resource only supports a fixed list of services, and a Pulumi dynamic provider cannot be used from the YAML runtime). So, exactly like the official integration, a `sandbox-deploy-{resource}` pipeline step calls that API after `pulumi up`: it resolves the pushed image to its immutable digest, creates the disk image from it (pulled with the group's identity), waits until it is ready, creates the sandbox (tier, environment variables, command, egress policy, workload identity), applies the lifecycle policy and exposes the ports. It authenticates with `DefaultAzureCredential` (e.g. `az login`) and retries 403s while the role assignment propagates. The previous generation of a sandbox is removed once the new one is up, and `aspire destroy` removes every sandbox and disk image this stack deployed to the group before `pulumi destroy` deletes it.

```csharp
var sandboxes = builder.AddPulumiSandboxGroup("sandboxes")
    .WithPulumiStack(azureStack)
    .WithSystemAssignedIdentity()                                   // or WithUserAssignedIdentity(identity) / WithNoManagedIdentity()
    // .WithAzureContainerRegistry(registry)                        // use your own Pulumi ACR instead of sandboxes-acr
    // .WithAcrPullIdentity(identity)                               // you then grant AcrPull yourself, as upstream
    // .PublishAsExisting("my-group", "my-rg")                      // existing group; needs WithAcrPullIdentity, and you grant the Data Owner role
    .ConfigureInfrastructure(infra => infra.SandboxGroup.Set("tags.team", "platform"));

var api = builder.AddProject<Projects.Api>("api")
    .WithExternalHttpEndpoints()
    .PublishAsAzureSandbox(new AzureSandboxOptions                  // optional; defaults to the Medium tier
    {
        Tier = AzureSandboxTier.Small,
        AutoSuspendEnabled = true, AutoSuspendInterval = TimeSpan.FromMinutes(15), AutoSuspendMode = AzureSandboxAutoSuspendMode.Disk,
        Endpoints = [new AzureSandboxEndpointOptions { Name = "http", Anonymous = true }],   // ports use Entra ID auth unless Anonymous
    });
```

`PublishAsAzureSandbox` also has an `Action<AzureSandboxOptions>` overload and is a no-op outside publish mode. `WithSandboxIdentity(identity)` runs a compute resource's sandbox as a Pulumi user-assigned identity (the identity is attached to the group and `AZURE_CLIENT_ID` is set, like `WithAzureUserAssignedIdentity` upstream). When a group is the only compute environment, resources target it automatically; otherwise call `WithComputeEnvironment`. Endpoints of one sandbox can be referenced from another (`WithReference`); the referencing sandbox is deployed after it and receives the public URL. Sandbox egress is deny-by-default and opened only for the hosts that appear in the sandbox's resolved environment variables and arguments (URLs and connection strings), as upstream. The deployment dashboard URL (`https://sandboxes.azure.com/sandbox-groups/...`) is added to the deployment summary.

**Resource provider.** Upstream's Bicep creates `Microsoft.App/sandboxGroups@2026-02-01-preview`. azure-native 3.29 only exposes `azure-native:containerinstance/v20260701:SandboxGroup`, which PUTs to `Microsoft.ContainerInstance/sandboxGroups`: that type does not exist in the Microsoft.ContainerInstance provider (`az provider show -n Microsoft.ContainerInstance` lists no sandbox types, while Microsoft.App lists `sandboxGroups` for `2026-07-01` and `2026-02-01-preview`), and the *Data Owner* role's data actions are `Microsoft.App/sandboxGroups/*`. So the group is created through azure-native's generic ARM resource (`azure-native:resources:Resource`, namespace `Microsoft.App`, type `sandboxGroups`, api-version `2026-02-01-preview`; override with `ConfigureInfrastructure(infra => infra.SandboxGroup.Set("apiVersion", "2026-07-01"))`). Its settings therefore sit under `properties.` as in the REST API. The group is named after the Aspire resource (ARM names are unique per resource group, so upstream's `uniqueString` suffix is not needed).

Limitations (all verified only against `pulumi preview` and `aspire do diagnostics`; nothing was deployed because it needs a subscription with Sandboxes preview access and incurs cost, and it is not demoed in `AppHost.cs`):

- The data-plane steps are pipeline code, not Pulumi resources: `pulumi up` shows only the group, registry and identities, and the sandboxes are not tracked in Pulumi state. Upstream keeps a local deployment-state file with a cross-process lease and retains the previous URL while rolling; this port tracks ownership with sandbox/disk image labels (`aspire-owner`, `aspire-resource`, `aspire-deploy`), deletes the previous generation after the new one is up, and does not garbage-collect sandboxes of resources removed from the AppHost until `aspire destroy`.
- Requires a container runtime that can inspect image manifests/config (Docker or Podman) and `az` for `acr login`.
- Container mounts and non-HTTP endpoints are rejected (as upstream). Sandbox URLs are only known after deployment, so they cannot feed Pulumi-provisioned values.

## Redis

`AspirePulumiPackages.Pulumi.Azure.Redis` ports `Aspire.Hosting.Azure.Redis`. `builder.AddPulumiAzureRedis("cache")` (alias `AddPulumiRedis`) provisions Azure Cache for Redis (`azure-native:redis:Redis`, Basic C1, TLS 1.2, non-SSL port off) and `builder.AddPulumiAzureManagedRedis("cache")` (alias `AddPulumiManagedRedis`) provisions Azure Managed Redis (`redisenterprise:RedisEnterprise` Balanced_B0 plus a `default` database on port 10000), matching the Bicep the official package generates. Both default to Microsoft Entra authentication (access keys disabled): `.WithReference(cache)` yields `ConnectionStrings__cache` (`host,ssl=true` / `host:10000,ssl=true`) and the hosting compute environment's identity gets the `Data Contributor` access policy.

var cache = builder.AddPulumiAzureRedis("cache").WithPulumiStack(azureStack).RunAsContainer();

## Kubernetes (AKS)

`AspirePulumiPackages.Pulumi.Azure.Kubernetes` ports `Aspire.Hosting.Azure.Kubernetes` (infrastructure) and the compute-deployment half of `Aspire.Hosting.Kubernetes`. `builder.AddPulumiKubernetes("aks")` (alias `AddPulumiAzureKubernetesEnvironment`) provisions an `azure-native:containerservice:ManagedCluster` matching the official Bicep: Free tier, system-assigned identity, an autoscaled `system` pool and a `workload` user pool (Standard_D2s_v5, 1-3 nodes), OIDC issuer and workload identity enabled, plus a Basic container registry (`{name}-acr`) whose `AcrPull` role is granted to the kubelet identity. Outputs (`ClusterFqdn`, `OidcIssuerUrl`, `KubeletIdentityObjectId`, `NodeResourceGroup`, `RegistryEndpoint`, ...) are exposed as `PulumiOutputReference` properties.

The environment is an `IComputeEnvironmentResource` (and `IContainerRegistry`, like the Container Apps environment): compute resources that target it (the only compute environment, or `WithComputeEnvironment(aks)`) are built, pushed to its registry and deployed with the Pulumi Kubernetes provider. The provider is configured from `listManagedClusterUserCredentials`, so a deploy needs only the stack, not a local kubeconfig. Per compute resource it emits a `ServiceAccount`, a `ConfigMap` (plain environment variables) and `Secret` (secret parameters), a `Deployment` (a `StatefulSet` when volumes are mounted, as upstream), pinned to the first user node pool, and a `ClusterIP` `Service` named `{name}-service` (what other workloads resolve through `GetHostAddressExpression`).

```csharp
var aks = builder.AddPulumiKubernetes("aks").WithPulumiStack(azureStack).WithResourceGroup(sharedRg)
    .WithSystemNodePool("Standard_D4s_v5", 1, 5)
    .WithContainerRegistry(registry)           // instead of the default '{name}-acr'
    .WithSubnet(nodesSubnet)                   // plain (non-delegated) subnet from the Network package
    .WithNetworkProfile(networkPolicy: "azure")   // typed options (upstream has no public setter)
    .AsPrivateCluster(privateDnsZone);         // or AsPrivateCluster() for the AKS-managed zone
aks.AddNodePool("gpu", "Standard_NC4as_T4_v3", 0, 2);   // user pool, optional .WithSubnet(...)

var data = aks.AddPersistentVolume("data").WithCapacity("20Gi");
var api = builder.AddProject<Projects.Api>("api").WithExternalHttpEndpoints()
    .WithPersistentVolume(data, "/data", env: "DATA_PATH");

var lb = aks.AddLoadBalancer("lb", albSubnet);          // Application Gateway for Containers
var cm = aks.AddCertManager("cert-manager");
var issuer = cm.AddIssuer("letsencrypt").WithLetsEncryptProduction("me@example.com").WithHttp01Solver();
aks.AddGateway("public").WithHostname("example.com").WithRoute("/", api.GetEndpoint("http")).WithTls(issuer).WithLoadBalancer(lb);
aks.AddIngress("legacy").WithIngressClass("nginx").WithPath("/api", api.GetEndpoint("http")).WithTls();
aks.AddHelmChart("metrics", "oci://registry-1.docker.io/bitnamicharts/metrics-server", "7.2.0").WithHelmValue("replicas", "2");
```

What each piece becomes (verified against the official publisher's output with a throwaway AppHost, and `pulumi preview` type-checks the generated program):

- **Workload identity (per-workload federated credentials).** Upstream creates one user-assigned identity per compute resource; here the environment owns one shared user-assigned identity (`{name}` + `Identity`, like the Container Apps environment's pull identity) and each workload's service account `{name}-sa` gets its own `FederatedIdentityCredential` on it (issuer = the cluster's OIDC issuer, subject `system:serviceaccount:default:{name}-sa`, audience `api://AzureADTokenExchange`; credentials are chained because Azure rejects concurrent writes to one identity). Because the environment implements `IPulumiManagedIdentityResource`, every integration that grants roles to a referencing app's compute environment (Storage, Service Bus, Key Vault, ...) works unchanged. The pods carry `azure.workload.identity/use`, so the workload-identity webhook injects `AZURE_CLIENT_ID`/`AZURE_TENANT_ID`/token file. The 20-credential-per-identity Azure limit applies to the shared identity.
- **Network profile / private cluster.** `WithNetworkProfile(plugin, policy, serviceCidr, dnsServiceIP)` (defaults Azure CNI, Calico, 10.0.4.0/22, 10.0.4.10) and `AsPrivateCluster()`. With a Pulumi private DNS zone, `AsPrivateCluster(zone)` switches the control plane to a user-assigned identity holding Private DNS Zone Contributor on the zone and Network Contributor on its VNet. As upstream, a node subnet implies `networkPlugin: azure` when no profile is set.
- **`AddIngress` / `AddGateway`** produce a `networking.k8s.io/v1` Ingress and a Gateway API `Gateway` + `HTTPRoute` (http listener on 80, https on 443 when TLS is set) with the upstream `With*` surface (class, hostnames, paths/routes, TLS, annotations, default backend). Routed endpoints must be external, as upstream enforces. Gateway API objects, ClusterIssuers and the ALB are applied as `kubernetes:yaml/v2:ConfigGroup` (Pulumi YAML does not support `CustomResource`).
- **`AddHelmChart`** is a `kubernetes:helm.sh/v3:Release` (OCI or URL chart references; `helm --set` style dotted keys are expanded and `true`/integers typed). External charts are retained on `pulumi destroy` unless `WithDestroy()` (upstream's `aspire destroy` behaviour); `WithForceConflicts()` maps to the release's `takeOwnership`, the closest equivalent of `--force-conflicts`. `AddCertManager` installs cert-manager (default `v1.20.2`, `crds.enabled`, Gateway API support) into the `cert-manager` namespace and `AddIssuer(...).WithLetsEncrypt*/WithAcmeServer/WithHttp01Solver` creates the `ClusterIssuer`s.
- **`AddLoadBalancer`** (Application Gateway for Containers) switches the cluster to the `2025-09-02-preview` AKS API (`azure-native:containerservice/v20250902preview:ManagedCluster`, required for `ingressProfile.gatewayAPI` / `applicationLoadBalancer`, as upstream), delegates the subnet to `Microsoft.ServiceNetworking/trafficControllers`, grants the ALB controller identity Network Contributor on it and applies the `ApplicationLoadBalancer` custom resource. A pipeline step (`aks-wait-alb-{name}`) polls for the `azure-alb-external` GatewayClass with `az`/`kubectl` before the deploy, like upstream's `apply-alb-crd` step; without `kubectl` it only warns and a second deploy may be needed.
- **`AddPersistentVolume`** is a `PersistentVolumeClaim` (capacity, storage class, access modes, annotations); `WithPersistentVolume(volume, path[, env])` mounts it, and a plain `WithVolume(...)` gets its own 1Gi claim.

Also `WithWorkloadIdentity(bool)` and `WithContainerInsights(logAnalyticsWorkspace)` (Log Analytics wiring via the `omsagent` add-on; upstream only exposes this as a property). The resource types keep the upstream names (`KubernetesIngressResource`, `CertManagerResource`, ...) but are Pulumi-side types in `AspirePulumiPackages.Pulumi.Azure.Kubernetes`, so do not reference `Aspire.Hosting.Kubernetes` in the same AppHost. Not demoed in the sample AppHost because a running AKS cluster (two nodes) has real ongoing cost.

Differences and limits: the Aspire dashboard component upstream adds to the cluster and `PublishAsKubernetesService`/Helm chart customization hooks are not ported (use `ConfigureInfrastructure` or a Helm release); bind mounts are ignored (warning); Helm chart references from `helm repo add` aliases are not supported (use OCI or URL references); everything is deployed to the `default` namespace; secret handling covers parameters marked secret (a connection string that embeds one is detected too) but secrets still land in Pulumi state, encrypted. Private clusters need the deploying machine to reach the cluster's VNet. `pulumi preview` was run against the generated programs (type-checked, nothing created); `pulumi up` against Azure was not, since it creates paid resources.

## Resource groups

Resources built on the shared `AspirePulumiPackages.Pulumi.Azure.Base` layer (e.g. `AddPulumiAzureUserAssignedIdentity`) create their own resource group by default. To put several of them in one shared resource group instead, provision it explicitly and point each resource at it with `WithResourceGroup`:

```csharp
var sharedRg = builder.AddPulumiAzureResourceGroup("shared-rg")
    .WithPulumiStack(azureStack);

var workloadIdentity = builder.AddPulumiAzureUserAssignedIdentity("workload-identity")
    .WithPulumiStack(azureStack)
    .WithResourceGroup(sharedRg);
```

Both resources must be bound to the same Pulumi stack — `WithResourceGroup` is a same-program `${sharedRg.name}` reference, not a cross-stack output lookup — and binding them to different stacks throws a clear error instead of generating broken YAML. `WithExistingResourceGroup("name")` is still available for pointing at a resource group Pulumi doesn't manage at all.

## Multiple stacks

Resources can be split across separate Pulumi stacks (own project, own ESC environment) by adding more than one `AddPulumiStack` and binding each resource to the stack it belongs to with `.WithPulumiStack(...)`:

```csharp
var appName = "aspire-pulumi-packages";

var entraStack = builder.AddPulumiStack($"{appName}-entra", "entra-test")
    .WithProjectName(appName)
    .WithOrganization("two4suited")
    .WithEscEnvironment("entra/test");

builder.AddPulumiAzureAdAppRegistration("app-registration")
    .WithPulumiStack(entraStack);

var azureStack = builder.AddPulumiStack(appName, "azure-test")
    .WithProjectName(appName)
    .WithOrganization("two4suited")
    .WithEscEnvironment("azure/test")
    .DependsOnStack(entraStack);

var acaEnv = builder.AddPulumiAzureContainerAppEnvironment("aca-env")
    .WithPulumiStack(azureStack);
```

Once there is more than one `PulumiStackResource` in the model, every stack-bound resource must call `.WithPulumiStack(...)` explicitly — the "only stack in the model" fallback used for a single-stack app no longer applies.

`.WithProjectName(...)` overrides the Pulumi project name (which otherwise defaults to the Aspire resource name), so several stacks — each still its own Aspire resource, own generated Pulumi project directory, own stack name — can be grouped under one shared Pulumi project in the backend. Above, both stacks declare `name: "aspire-pulumi-packages"` in their generated `Pulumi.yaml`, differing only by stack: `two4suited/aspire-pulumi-packages/azure-test` and `two4suited/aspire-pulumi-packages/entra-test`.

Chain `.DependsOnStack(...)` onto a stack (as above) to order two stacks' deploys — it makes `aspire deploy` fully deploy the dependency before provisioning this stack's infrastructure. It only wires the two stacks' provision/deploy pipeline steps together (tagged `ProvisionInfrastructure`/`DeployCompute`), so it has no effect on `aspire publish` (which never touches those steps). It does **not** by itself fix the two-deploy caveat below — each stack's Pulumi project (and any output values baked into it, like `AzureAd__ClientId`) is still generated independently during its own publish step, which isn't affected by this ordering.

## Azure AD app registration

`builder.AddPulumiAzureAdAppRegistration("app-registration")` provisions an `azuread:Application` plus a `azuread:ServicePrincipal` (via the `azuread` Pulumi provider) in whichever stack it's bound to with `.WithPulumiStack(...)`. Use `.WithDisplayName(...)` to override the display name (defaults to the resource name). The ESC environment bound to that stack must supply the `azuread` provider's credentials (tenant, client id/secret or OIDC), the same way `azure/test` supplies `azure-native`'s.

The resource exposes `ClientId`, `ObjectId` and `ServicePrincipalObjectId` as `PulumiOutputReference`s, so they can be fed into another resource's config the same way any Aspire reference is:

```csharp
var appRegistration = builder.AddPulumiAzureAdAppRegistration("app-registration")
    .WithPulumiStack(entraStack);

builder.AddProject<Projects.AspirePulumiPackages_Api>("api")
    .WithComputeEnvironment(acaEnv)
    .WithEnvironment("AzureAd__ClientId", appRegistration.Resource.ClientId);
```

These outputs are read with `pulumi stack output` from the `entra-app` stack, not resolved as a live Pulumi cross-stack reference. Because the API references `appRegistration`, the main stack's provision step is ordered after `entra-app`'s deploy step automatically (no `DependsOnStack`/`WaitFor` needed, though both still work), and the main program is regenerated after that, so the client id resolves on the first `aspire deploy`.
