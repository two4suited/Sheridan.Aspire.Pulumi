# Sheridan.Aspire.Pulumi

Aspire hosting integrations that provision Azure infrastructure with [Pulumi](https://www.pulumi.com) instead of Bicep/ARM. Each package mirrors the official `Aspire.Hosting.Azure.*` integration (`AddPulumiX` instead of `AddAzureX`, same `WithX` calls), so swapping Bicep for Pulumi is a drop-in change in your AppHost.

## Packages

All packages are published to GitHub Packages (NuGet) when a `vX.Y.Z` tag is pushed. The package id equals the project folder name under `src/`.

| Package | Purpose |
| --- | --- |
| [`Sheridan.Aspire.Pulumi`](src/Sheridan.Aspire.Pulumi) | Core: `PulumiStackResource`, `PulumiProgram`, `PulumiCli`, YAML generation, `AddPulumiStack`/`DependsOnStack` |
| [`Sheridan.Aspire.Pulumi.Provisioning`](src/Sheridan.Aspire.Pulumi.Provisioning) | `ConfigureInfrastructure` helpers (`PulumiInfrastructure`, `PulumiExpr`) |
| [`Sheridan.Aspire.Pulumi.Azure`](src/Sheridan.Aspire.Pulumi.Azure) | Shared Azure interfaces (managed identity, container app customization) |
| [`Sheridan.Aspire.Pulumi.Azure.Base`](src/Sheridan.Aspire.Pulumi.Azure.Base) | Azure base resources, resource groups, identities, role definitions, naming |
| `Sheridan.Aspire.Pulumi.Azure.<Service>` (folder under `src/`) | One package per service: AppConfiguration, AppContainers, AppService, ApplicationInsights, CognitiveServices, ConnectorNamespace, ContainerRegistry, CosmosDB, EntraId, EventHubs, Foundry, FrontDoor, Functions, KeyVault, Kubernetes, Kusto, Network, OperationalInsights, PostgreSQL, Redis, Sandboxes, Search, ServiceBus, SignalR, Sql, Storage, WebPubSub |
| [`Sheridan.Aspire.Pulumi.Entra`](src/Sheridan.Aspire.Pulumi.Entra) | Azure AD app registration |

Install the packages you need, for example:

```bash
dotnet add package Sheridan.Aspire.Pulumi.Azure.AppContainers
dotnet add package Sheridan.Aspire.Pulumi.Azure.CosmosDB
```

(Add `https://nuget.pkg.github.com/<owner>/index.json` as a NuGet source with a token that has `read:packages`.) Namespaces match the package ids.

## Pulumi integration

In your AppHost, declare a Pulumi stack with `builder.AddPulumiStack("my-app", "dev").WithOrganization("my-org")`. There is no separate Pulumi project; it is generated by the Aspire pipeline:

- `aspire publish` writes `Pulumi.yaml` and `Pulumi.<stack>.yaml` (which imports the ESC environment) to `<output>/<name>/pulumi/`.
- `aspire deploy` then checks `pulumi whoami` (run `pulumi login` first), creates the ESC environment and stack if missing, and runs `pulumi up`. State lives in Pulumi Cloud.
- `aspire do pulumi-destroy-<name>` / `aspire destroy` runs `pulumi destroy`.

The stack name defaults to the lower-cased Aspire environment, so `aspire deploy -e test` targets stack `test` and `aspire deploy -e prod` targets `prod` (pass a second argument to `AddPulumiStack` to pin it).

Both can also be passed at the command line, overriding the code: `aspire deploy -- --Pulumi:Stack=qa --Pulumi:Esc=shared/qa,myproj/qa` (comma-separated list; also settable via config or the `Pulumi__Stack` / `Pulumi__Esc` environment variables).

Use `.WithEscEnvironment("project/env1", "project/env2")` to import one or more existing ESC environments (later ones override earlier ones); with none specified, `<name>/<stack>` is used and created on deploy if missing.

## Resource naming

Azure names are built from the app (Pulumi project) name, the Aspire resource name and the stack name, shortened deterministically (with a hash only when lossy) to fit each resource type's limits, and can be pinned with `WithAzureName(AzureNameKind.X, "name")`. See [docs/naming.md](docs/naming.md) for the scheme and the per-resource rule table.

## Multiple stacks

Resources can be split across separate Pulumi stacks (own project, own ESC environment) by adding more than one `AddPulumiStack` and binding each resource to the stack it belongs to with `.WithPulumiStack(...)`:

```csharp
var appName = "aspire-pulumi-packages";

var entraStack = builder.AddPulumiStack($"{appName}-entra", "entra-test")
    .WithProjectName(appName)
    .WithOrganization("two4suited")
    .WithEscEnvironment("entra/test");

builder.AddPulumiAzureAdAppRegistration("app-registration")
    .WithPulumiStack(entraStack);

var azureStack = builder.AddPulumiStack(appName, "azure-test")
    .WithProjectName(appName)
    .WithOrganization("two4suited")
    .WithEscEnvironment("azure/test")
    .DependsOnStack(entraStack);

var acaEnv = builder.AddPulumiAzureContainerAppEnvironment("aca-env")
    .WithPulumiStack(azureStack);
```

Once there is more than one `PulumiStackResource` in the model, every stack-bound resource must call `.WithPulumiStack(...)` explicitly — the "only stack in the model" fallback used for a single-stack app no longer applies.

`.WithProjectName(...)` overrides the Pulumi project name (which otherwise defaults to the Aspire resource name), so several stacks — each still its own Aspire resource, own generated Pulumi project directory, own stack name — can be grouped under one shared Pulumi project in the backend. Above, both stacks declare `name: "aspire-pulumi-packages"` in their generated `Pulumi.yaml`, differing only by stack: `two4suited/aspire-pulumi-packages/azure-test` and `two4suited/aspire-pulumi-packages/entra-test`.

Chain `.DependsOnStack(...)` onto a stack (as above) to order two stacks' deploys — it makes `aspire deploy` fully deploy the dependency before provisioning this stack's infrastructure. It only wires the two stacks' provision/deploy pipeline steps together (tagged `ProvisionInfrastructure`/`DeployCompute`), so it has no effect on `aspire publish` (which never touches those steps). It does **not** by itself fix the two-deploy caveat below — each stack's Pulumi project (and any output values baked into it, like `AzureAd__ClientId`) is still generated independently during its own publish step, which isn't affected by this ordering.
