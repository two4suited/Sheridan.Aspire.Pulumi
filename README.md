# aspire.pulumi.packages

## Pulumi integration

`AppHost.cs` declares a Pulumi stack with `builder.AddPulumiStack("aspire-pulumi-packages", "dev").WithOrganization("two4suited")`. There is no separate Pulumi project; it is generated by the Aspire pipeline:

- `aspire publish` writes `Pulumi.yaml` and `Pulumi.<stack>.yaml` (which imports the ESC environment) to `<output>/<name>/pulumi/`.
- `aspire deploy` then checks `pulumi whoami` (run `pulumi login` first), creates the ESC environment and stack if missing, and runs `pulumi up`. State lives in Pulumi Cloud.
- `aspire do pulumi-destroy-<name>` / `aspire destroy` runs `pulumi destroy`.

The stack name defaults to the lower-cased Aspire environment, so `aspire deploy -e test` targets stack `test` and `aspire deploy -e prod` targets `prod` (pass a second argument to `AddPulumiStack` to pin it).

Both can also be passed at the command line, overriding the code: `aspire deploy -- --Pulumi:Stack=qa --Pulumi:Esc=shared/qa,myproj/qa` (comma-separated list; also settable via config or the `Pulumi__Stack` / `Pulumi__Esc` environment variables).

Use `.WithEscEnvironment("project/env1", "project/env2")` to import one or more existing ESC environments (later ones override earlier ones); with none specified, `<name>/<stack>` is used and created on deploy if missing.

The code is split across three class libraries under `src/`: `AspirePulumiPackages.Pulumi` (the stack/pipeline/YAML-generation core — `PulumiStackResource`, `PulumiProgram`, `PulumiCli`, `PulumiOutputReference`, `AddPulumiStack`/`DependsOnStack`/etc.), `AspirePulumiPackages.Pulumi.Azure` (the shared managed-identity interface); Cosmos DB lives in `AspirePulumiPackages.Pulumi.Azure.CosmosDB`; the Container Apps environment lives in `AspirePulumiPackages.Pulumi.Azure.AppContainers` (port of `Aspire.Hosting.Azure.AppContainers`: `WithAzureContainerRegistry`, `WithAzureLogAnalyticsWorkspace`, `WithAcrPullIdentity`, `WithDashboard`, VNet via `WithDelegatedSubnet`, and `PublishAsPulumiContainerAppJob`/`PublishAsScheduledPulumiContainerAppJob`), and `AspirePulumiPackages.Pulumi.Entra` (the Azure AD app registration). Azure and Entra both depend on the core project; `AspirePulumiPackages.AppHost` references all three.

## Container Apps environment

`builder.AddPulumiAzureContainerAppEnvironment("aca-env")` is the Pulumi equivalent of Aspire's `AddAzureContainerAppEnvironment`. It is a compute environment, so resources opt in the usual way:

```csharp
var acaEnv = builder.AddPulumiAzureContainerAppEnvironment("aca-env");
builder.AddProject<Projects.AspirePulumiPackages_Api>("api")
    .WithExternalHttpEndpoints()
    .WithComputeEnvironment(acaEnv);
```

`aspire publish` writes the resource group, Log Analytics workspace, container registry, pull identity (AcrPull) and managed environment, plus a `ContainerApp` per targeted resource. `aspire deploy` runs: `pulumi-provision` (login, ESC, `pulumi up --target` for the infrastructure incl. the registry) → `build-<resource>` → `push-<resource>` → `pulumi-deploy` (full `pulumi up`). Images are tagged with a per-deploy timestamp so each deploy creates a new revision.

## Cosmos DB

`builder.AddPulumiCosmosDB("cosmos")` is the Pulumi equivalent of Aspire's `AddAzureCosmosDB`: a serverless NoSQL API account with Entra-only auth (`disableLocalAuth: true` — no connection-string keys in the cloud). Databases and containers are added the same way as the official integration:

```csharp
var cosmos = builder.AddPulumiCosmosDB("cosmos")
    .WithPulumiStack(azureStack)
    .RunAsEmulator();
cosmos.AddCosmosDatabase("appdb").AddContainer("items", "/id");

builder.AddProject<Projects.AspirePulumiPackages_Api>("api")
    .WithComputeEnvironment(acaEnv)
    .WithReference(cosmos);
```

Package: `AspirePulumiPackages.Pulumi.Azure.CosmosDB` (port of `Aspire.Hosting.Azure.CosmosDB`; `AddPulumiAzureCosmosDB` remains as an alias). Also supported: `AddCosmosDatabase(name, databaseName?)`/`AddContainer(name, partitionKeyPath(s), containerName?)` with per-database/container connection strings, `WithDefaultAzureSku()` (non-serverless), `RunAsEmulator`/`RunAsPreviewEmulator`/`RunAsClassicEmulator` (+ `WithDataVolume`, `WithGatewayPort`, `WithPartitionCount`, `WithDataExplorer`), `ConfigureInfrastructure(i => i.CosmosDBAccount.Set(...))`, and `WithAccessKeyAuthentication()`, which keeps local auth on and stores the account/database/container connection strings and primary key as secrets in a Key Vault created for the account (consumers get Key Vault Secrets User; the connection string expression resolves to the secret URI, as with `AddPulumiAzureKeyVault(...).GetSecret`).

`.RunAsEmulator()` runs the Cosmos DB NoSQL API emulator container locally (no effect in publish mode) so `aspire run` works without any Azure resources. `aspire publish`/`aspire deploy` provision the real account, database(s) and container(s) instead.

`.WithReference(cosmos)` on a project is enough to get data access — no separate role-assignment call is needed. Any compute environment (e.g. `AddPulumiAzureContainerAppEnvironment`) hosting a resource that references the Cosmos DB account automatically gets a Pulumi `SqlResourceSqlRoleAssignment` granting its shared managed identity the built-in **Cosmos DB Built-in Data Contributor** role, scoped to the account — the data-plane equivalent of the ACR pull role assignment described above. `ConnectionStrings__cosmos` (the account's document endpoint, consumed by `Microsoft.Azure.Cosmos`/`Aspire.Microsoft.Azure.Cosmos` with `DefaultAzureCredential`) is read from the stack's outputs the same way `AzureAd__ClientId` is above, so it's subject to the same "deploy once to create the account, deploy again to pick up the endpoint" caveat on the first deploy.

## Storage

`AspirePulumiPackages.Pulumi.Azure.Storage` ports `Aspire.Hosting.Azure.Storage`. `builder.AddPulumiStorage("storage")` (alias `AddPulumiAzureStorage`) provisions a StorageV2 / Standard_GRS / TLS1_2 account with shared-key access disabled, matching the Bicep the official integration generates. `AddBlobs`/`AddQueues`/`AddTables`, `AddBlobContainer` and `AddQueue` mirror the official API, and `.RunAsEmulator()` runs Azurite locally. `WithReference(blobs)` (or the queue/table/container/queue resources) grants the hosting compute environment's identity the matching *Storage Blob/Queue/Table Data Contributor* role. The storage account name is auto-generated by the azure-native provider.

## Azure Functions

`AspirePulumiPackages.Pulumi.Azure.Functions` ports `Aspire.Hosting.Azure.Functions`. `builder.AddPulumiAzureFunctionsProject("func", "../MyFunctions/MyFunctions.csproj")` (or `<TProject>`; alias `AddPulumiFunctionsProject`) mirrors `AddAzureFunctionsProject`: a `ProjectResource` that sets the Functions environment variables (`FUNCTIONS_WORKER_RUNTIME`, OpenTelemetry mode, `ASPNETCORE_URLS`) and wires host storage as `AzureWebJobsStorage__{blob,queue,table,dataLake}ServiceUri` (identity-based).

```csharp
var storage = builder.AddPulumiStorage("storage").WithPulumiStack(azureStack).RunAsEmulator();
var blobs = storage.AddBlobs("blobs");

builder.AddPulumiAzureFunctionsProject("func", "../MyFunctions/MyFunctions.csproj")
    .WithPulumiStack(azureStack)      // binds the implicit host storage account
    // .WithHostStorage(storage)      // or use your own Pulumi storage account instead of the implicit one
    .WithReference(blobs)             // injects blobs__blobServiceUri etc. (not ConnectionStrings__blobs), as upstream
    .WithComputeEnvironment(acaEnv);
```

By default an implicit `funcstorage<hash>` storage account is created (Azurite in run mode; dropped from the model if every project uses `WithHostStorage`). Deployed through `AddPulumiAzureContainerAppEnvironment`, the container app gets `kind: functionapp` (KEDA scale rules follow the triggers), `http` ingress and no 1-replica cap; the environment identity is granted Storage Blob/Queue/Table Data Contributor (via the Storage integration) plus Storage Account Contributor on the host storage, matching the official Bicep. The compute environment hook is `PulumiContainerAppCustomizationAnnotation` in `AspirePulumiPackages.Pulumi.Azure`. Not ported: launch-profile port discovery in run mode, `AZURE_CLIENT_ID` injection (the shared environment identity is not exposed with a client id yet), the Durable Task scheduler APIs. Like the other integrations, storage endpoints are read from stack outputs, so the very first deploy needs a second `aspire deploy`.

## Search

`AspirePulumiPackages.Pulumi.Azure.Search` ports `Aspire.Hosting.Azure.Search`. `builder.AddPulumiSearch("search")` (alias `AddPulumiAzureSearch`) provisions an `azure-native:search:Service` matching the Bicep the official integration generates: `basic` SKU, 1 partition, 1 replica, `hostingMode: default` and local (key) auth disabled, with outputs `Endpoint` (`https://<name>.search.windows.net`), `Name` and `Id`. The connection string is `Endpoint=<endpoint>`. `WithReference(search)` grants the hosting compute environment's identity *Search Index Data Contributor* and *Search Service Contributor* (the official defaults); `WithRoleAssignments(search, AzureSearchRole.SearchIndexDataReader, ...)` replaces them. `WithSku("standard")` is an addition for choosing another tier, and `ConfigureInfrastructure(infra => infra.SearchService.Set("replicaCount", 3))` edits the generated resource (see `docs/provisioning.md`). The service name is auto-generated by the azure-native provider. Not ported: `PublishAsExisting`/`AsExisting`, and a local emulator (the official integration has none).

## Service Bus

`AspirePulumiPackages.Pulumi.Azure.ServiceBus` ports `Aspire.Hosting.Azure.ServiceBus`. `builder.AddPulumiServiceBus("messaging")` (alias `AddPulumiAzureServiceBus`) provisions a Standard-SKU namespace with local auth disabled, matching the official Bicep (outputs `serviceBusEndpoint`, `serviceBusHostName`, `name`, `id`). `AddServiceBusQueue`/`AddServiceBusTopic`/`AddServiceBusSubscription` (plus the `AddQueue`/`AddTopic`/`AddSubscription` forms) and `WithProperties(...)` on queues, topics and subscriptions mirror the official API, including `Rules` (correlation filters) on subscriptions.

```csharp
var sb = builder.AddPulumiServiceBus("messaging").WithPulumiStack(azureStack);
sb.AddServiceBusQueue("orders").WithProperties(q => q.MaxDeliveryCount = 5);
sb.AddServiceBusTopic("events").AddServiceBusSubscription("audit");

builder.AddProject<Projects.AspirePulumiPackages_Api>("api").WithReference(sb).WithComputeEnvironment(acaEnv);
```

`WithReference` of the namespace, a queue, a topic or a subscription grants the hosting compute environment's identity *Azure Service Bus Data Owner* on the namespace (the official default); `WithRoleAssignments(sb, AzureServiceBusRole.AzureServiceBusDataSender, ...)` replaces it. The namespace name is auto-generated by the azure-native provider. Not ported: `RunAsEmulator` (the Service Bus emulator) and its configuration APIs.

## Key Vault

`builder.AddPulumiAzureKeyVault("vault")` (project `AspirePulumiPackages.Pulumi.Azure.KeyVault`) is the Pulumi equivalent of `AddAzureKeyVault`: a standard-SKU, RBAC-authorized vault (same shape as the official Bicep: `tenantId`, SKU `A/standard`, `enableRbacAuthorization`, `aspire-resource-name` tag) with outputs `vaultUri`, `name`, `id`. The vault URI is the connection string, so `.WithReference(vault)` yields `ConnectionStrings__vault`.

```csharp
var vault = builder.AddPulumiAzureKeyVault("vault")
    .WithPulumiStack(azureStack)
    .AddSecret("api-key", builder.AddParameter("api-key", secret: true));

builder.AddProject<Projects.AspirePulumiPackages_Api>("api")
    .WithComputeEnvironment(acaEnv)
    .WithRoleAssignments(vault, AzureKeyVaultRole.KeyVaultSecretsUser)  // optional; default is Key Vault Administrator, as in the official package
    .WithReference(vault);
```

Secret parameters become secret Pulumi config entries (`pulumi config set --secret apiKey ...`). Also supported: `PublishAsExisting`/`AsExisting`, `GetSecret(name)` (the secret URI, not a platform-resolved Key Vault reference) and the Pulumi-specific `WithDeployerRoleAssignments(...)` which grants the deploying principal roles (e.g. Secrets Officer) so Pulumi can write secrets under RBAC; secrets depend on that assignment. Not ported: `ReferenceExpression` secrets, `RunAsExisting`.

## Redis

`AspirePulumiPackages.Pulumi.Azure.Redis` ports `Aspire.Hosting.Azure.Redis`. `builder.AddPulumiAzureRedis("cache")` (alias `AddPulumiRedis`) provisions Azure Cache for Redis (`azure-native:redis:Redis`, Basic C1, TLS 1.2, non-SSL port off) and `builder.AddPulumiAzureManagedRedis("cache")` (alias `AddPulumiManagedRedis`) provisions Azure Managed Redis (`redisenterprise:RedisEnterprise` Balanced_B0 plus a `default` database on port 10000), matching the Bicep the official package generates. Both default to Microsoft Entra authentication (access keys disabled): `.WithReference(cache)` yields `ConnectionStrings__cache` (`host,ssl=true` / `host:10000,ssl=true`) and the hosting compute environment's identity gets the `Data Contributor` access policy.

```csharp
var cache = builder.AddPulumiAzureRedis("cache").WithPulumiStack(azureStack).RunAsContainer();
var managed = builder.AddPulumiAzureManagedRedis("managed").WithPulumiStack(azureStack)
    .WithAccessKeyAuthentication();                 // or .WithAccessKeyAuthentication(vault) with an AddPulumiAzureKeyVault resource
```

`WithAccessKeyAuthentication()` stores `connectionstrings--<name>` (and `primaryaccesskey--<name>` for Managed Redis) in a Key Vault created next to the cache (or the vault you pass, which needs `WithDeployerRoleAssignments(AzureKeyVaultRole.KeyVaultSecretsOfficer)`), and gives referencing environments *Key Vault Secrets User*. Also: `RunAsContainer` (local Redis container), `PublishAsExisting`/`AsExisting`, `WithSku` (Managed Redis). Differences: with access keys the connection string seen by a referencing app is the Key Vault secret **URI** (keys must not appear in stack outputs; Container Apps secret references are not generated), and `AsAzureRedis`/`PublishAsAzureRedis` (converting a stock `AddRedis`) and the polyglot variant are not ported.

## Application Insights

`builder.AddPulumiApplicationInsights("appinsights")` (project `AspirePulumiPackages.Pulumi.Azure.ApplicationInsights`) ports `AddAzureApplicationInsights`: a `web` Application Insights component (`azure-native:applicationinsights:Component`) backed by a Log Analytics workspace, with outputs `appInsightsConnectionString`, `name`, `id`. Without a workspace, a PerGB2018 workspace is created in the same resource group (as the official Bicep does). Link an existing one with `.WithLogAnalyticsWorkspace(law)` (a `AddPulumiLogAnalyticsWorkspace` resource bound to the same stack). The connection string is the resource's connection string, so `.WithReference(appInsights)` yields `ConnectionStrings__appinsights`.

## Resource groups

Resources built on the shared `AspirePulumiPackages.Pulumi.Azure.Base` layer (e.g. `AddPulumiAzureUserAssignedIdentity`) create their own resource group by default. To put several of them in one shared resource group instead, provision it explicitly and point each resource at it with `WithResourceGroup`:

```csharp
var sharedRg = builder.AddPulumiAzureResourceGroup("shared-rg")
    .WithPulumiStack(azureStack);

var workloadIdentity = builder.AddPulumiAzureUserAssignedIdentity("workload-identity")
    .WithPulumiStack(azureStack)
    .WithResourceGroup(sharedRg);
```

Both resources must be bound to the same Pulumi stack — `WithResourceGroup` is a same-program `${sharedRg.name}` reference, not a cross-stack output lookup — and binding them to different stacks throws a clear error instead of generating broken YAML. `WithExistingResourceGroup("name")` is still available for pointing at a resource group Pulumi doesn't manage at all.

## Multiple stacks

Resources can be split across separate Pulumi stacks (own project, own ESC environment) by adding more than one `AddPulumiStack` and binding each resource to the stack it belongs to with `.WithPulumiStack(...)`:

```csharp
var appName = "aspire-pulumi-packages";

var entraStack = builder.AddPulumiStack($"{appName}-entra", "entra-test")
    .WithProjectName(appName)
    .WithOrganization("two4suited")
    .WithEscEnvironment("entra/test");

builder.AddPulumiAzureAdAppRegistration("app-registration")
    .WithPulumiStack(entraStack);

var azureStack = builder.AddPulumiStack(appName, "azure-test")
    .WithProjectName(appName)
    .WithOrganization("two4suited")
    .WithEscEnvironment("azure/test")
    .DependsOnStack(entraStack);

var acaEnv = builder.AddPulumiAzureContainerAppEnvironment("aca-env")
    .WithPulumiStack(azureStack);
```

Once there is more than one `PulumiStackResource` in the model, every stack-bound resource must call `.WithPulumiStack(...)` explicitly — the "only stack in the model" fallback used for a single-stack app no longer applies.

`.WithProjectName(...)` overrides the Pulumi project name (which otherwise defaults to the Aspire resource name), so several stacks — each still its own Aspire resource, own generated Pulumi project directory, own stack name — can be grouped under one shared Pulumi project in the backend. Above, both stacks declare `name: "aspire-pulumi-packages"` in their generated `Pulumi.yaml`, differing only by stack: `two4suited/aspire-pulumi-packages/azure-test` and `two4suited/aspire-pulumi-packages/entra-test`.

Chain `.DependsOnStack(...)` onto a stack (as above) to order two stacks' deploys — it makes `aspire deploy` fully deploy the dependency before provisioning this stack's infrastructure. It only wires the two stacks' provision/deploy pipeline steps together (tagged `ProvisionInfrastructure`/`DeployCompute`), so it has no effect on `aspire publish` (which never touches those steps). It does **not** by itself fix the two-deploy caveat below — each stack's Pulumi project (and any output values baked into it, like `AzureAd__ClientId`) is still generated independently during its own publish step, which isn't affected by this ordering.

## Azure AD app registration

`builder.AddPulumiAzureAdAppRegistration("app-registration")` provisions an `azuread:Application` plus a `azuread:ServicePrincipal` (via the `azuread` Pulumi provider) in whichever stack it's bound to with `.WithPulumiStack(...)`. Use `.WithDisplayName(...)` to override the display name (defaults to the resource name). The ESC environment bound to that stack must supply the `azuread` provider's credentials (tenant, client id/secret or OIDC), the same way `azure/test` supplies `azure-native`'s.

The resource exposes `ClientId`, `ObjectId` and `ServicePrincipalObjectId` as `PulumiOutputReference`s, so they can be fed into another resource's config the same way any Aspire reference is:

```csharp
var appRegistration = builder.AddPulumiAzureAdAppRegistration("app-registration")
    .WithPulumiStack(entraStack);

builder.AddProject<Projects.AspirePulumiPackages_Api>("api")
    .WithComputeEnvironment(acaEnv)
    .WithEnvironment("AzureAd__ClientId", appRegistration.Resource.ClientId);
```

These outputs are read with `pulumi stack output` from the **already-deployed** `entra-app` stack, not resolved as a live Pulumi cross-stack reference. On the first `aspire deploy`, before `entra-app` has ever been deployed, the lookup fails and the env var is skipped (logged as a warning) — deploy once, then deploy again to pick up the client id.
