# Sheridan.Aspire.Pulumi.Azure.Storage

Azure Storage (blobs, queues, tables) provisioned by Pulumi, a drop-in for `AddAzureStorage`.

`AddPulumiStorage` provisions a StorageV2 / Standard_GRS / TLS 1.2 account with shared-key access disabled, matching the Bicep the official integration generates.

## Install

```bash
dotnet add package Sheridan.Aspire.Pulumi.Azure.Storage
```

## Usage

```csharp
var builder = DistributedApplication.CreateBuilder(args);

builder.AddPulumiStack("my-app", "dev").WithOrganization("my-org");

var acaEnv = builder.AddPulumiAzureContainerAppEnvironment("aca-env");   // Sheridan.Aspire.Pulumi.Azure.AppContainers

var storage = builder.AddPulumiStorage("storage")
    .RunAsEmulator();   // Azurite for `aspire run`
var blobs = storage.AddBlobs("blobs");
blobs.AddBlobContainer("uploads");
storage.AddQueues("queues").AddQueue("jobs");

builder.AddProject<Projects.MyApi>("api")
    .WithComputeEnvironment(acaEnv)
    .WithReference(blobs);

builder.Build().Run();
```

## Features

- `AddBlobs`, `AddQueues`, `AddTables`, `AddBlobContainer` and `AddQueue` mirror the official API.
- `WithReference(blobs)` (or the queue, table or container resources) grants the compute environment's identity the matching *Storage Blob/Queue/Table Data Contributor* role.
- The storage account name is auto-generated by the azure-native provider. Alias: `AddPulumiAzureStorage`.

## Azurite emulator

`RunAsEmulator` runs Azurite (`mcr.microsoft.com/azure-storage/azurite`, pinned to the tag the official integration uses) in `aspire run` instead of the Pulumi-provisioned account. It has no effect when publishing. The container is started with the same arguments as the official integration (`azurite -l /data --blobHost 0.0.0.0 --queueHost 0.0.0.0 --tableHost 0.0.0.0 --disableProductStyleUrl --skipApiVersionCheck`), so recent `Azure.Storage` SDKs are not rejected with "API version not supported".

```csharp
var storage = builder.AddPulumiStorage("storage")
    .RunAsEmulator(emulator => emulator
        .WithDataVolume()            // or WithDataBindMount(".azurite/storage")
        .WithBlobPort(10000)
        .WithQueuePort(10001)
        .WithTablePort(10002));
```

`configureContainer` receives an `IResourceBuilder<AzureStorageEmulatorResource>` with:

- `WithDataVolume(name?, isReadOnly)` / `WithDataBindMount(path?, isReadOnly)`: persist `/data` between runs (default bind-mount path `.azurite/{storage name}`).
- `WithBlobPort(port)` / `WithQueuePort(port)` / `WithTablePort(port)`: fixed host ports (random otherwise).
- `WithApiVersionCheck(enable = true)`: remove `--skipApiVersionCheck` so Azurite validates the requested API version. Note this differs from the official integration, whose implementation adds the flag when `enable` is `true`, contradicting its documentation.

### Declared containers and queues are created in Azurite

Blob containers added with `AddBlobContainer` and queues added with `AddQueue` (also through `AddBlobs(...).AddBlobContainer` / `AddQueues(...).AddQueue`) are created in the emulator with `CreateIfNotExistsAsync` once Azurite is healthy, the way the official `RunAsEmulator` does. The emulator container has a health check, and anything that references the storage account or one of its children waits for the account to be `Running`, i.e. for that creation step to finish. If creation fails, the account and its children are marked `FailedToStart` and the error is written to the account's log.

## Emulator, existing account or deployed account

| Mode | Call | In `aspire run` | When publishing |
| --- | --- | --- | --- |
| Emulator | `RunAsEmulator()` | Azurite container; containers and queues are created in it | Pulumi creates the account |
| Existing | `AsExisting(name, resourceGroup?)` / `PublishAsExisting(...)` plus `RunAsExisting(...)` | the endpoints you supply, nothing to deploy | Pulumi looks the account up (`azure-native:storage:getStorageAccount`) instead of creating it; containers, queues and role assignments are still applied to it |
| Deployed | none | endpoints from the deployed Pulumi stack outputs, so the stack has to be generated and deployed first | Pulumi creates the account |

```csharp
// Publish against a shared account; use the same account when running locally.
var storage = builder.AddPulumiStorage("storage")
    .AsExisting("sharedacct", "shared-rg")   // PublishAsExisting is the same call
    .RunAsExisting("sharedacct");            // or a ParameterResource builder with the account name
```

`RunAsExisting` takes a bare account name, a host such as `sharedacct.blob.core.windows.net`, or a service URL; the account name (and the cloud's endpoint suffix) are taken from it and the blob, queue, table and Data Lake endpoints derived. With a `ParameterResource` the parameter value is the account name. Clients use the developer's Azure credentials (`DefaultAzureCredential`) against the real account, so the account has to grant them a data-plane role. `RunAsExisting` and `RunAsEmulator` are mutually exclusive, and `RunAsExisting` has no effect when publishing. Without either, referencing a storage child in `aspire run` fails with `Pulumi project for '...' has not been generated yet`.
